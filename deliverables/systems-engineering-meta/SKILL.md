## 适用条件

**适用**（任一命中即召回）：
- 新系统顶层设计：多模块、跨边界、有性能/安全/成本/时间硬约束
- 重大重构：模块边界或数据流需重新划定
- 项目无 Blueprint.md 且任务复杂度超出单计划承载

**不适用**：
- 单文件脚本、一次性原型、探索性 spike（§10.1 域错配：重机制白付对碰税）
- 纯实现任务（设计已明确，直接 /plan）
- 已有成熟架构的小幅增量（只改局部，不动边界）

**根因**：领域专家的门槛不是"不会写设计"，而是"不熟悉系统工程方法论"
（边界/接口/约束/验收怎么划）。本技能把方法论外包给阳；元只做他本能
擅长的事——判断领域后果是否符合直觉。

## 操作程序

方向反转：普通技能指导阳做事，本技能指导阳**向元提问**。全程领域语言，
不问技术选型。**问先于写**——禁止一次性生成完整草稿再求确认。

1. 意图澄清：问"要解决什么领域问题"，不问"要什么技术"。
2. 边界划定：系统内/系统外/明确不做，逐项向元确认。
3. 接口定义：模块怎么交互、数据怎么流（文字或 Mermaid 数据流）。
4. 约束识别：区分硬约束（违反即失败）与软约束（可权衡）。
5. 验收标准：怎么证明"做对了"，用领域语言、元可检验。
6. 双语翻译：每个技术决策附领域后果——"选 X → 好处 A，代价 B"，
   元只需确认 A/B 是否符合领域直觉。
7. 方案预演：自然语言模拟主要场景，至少暴露一个潜在冲突并记录。
8. 成稿 `Blueprint.draft.md`：§1 边界 / §2 接口 / §3 约束 / §4 验收
   ＋「元问答」节（≥3 个领域问题及元的回答，防橡皮图章）
   ＋「预演冲突」节。
9. 结构自检 + 呈批：跑「验证凭证」的 grep，输出随草稿一并呈元。
   **批准/拒绝由元裁决，阳不得代裁（能垒）**。批准后并入 Blueprint.md
   并落章节编号——下游计划以 blueprint: §x.y 锚引用，悬空引用归 R6 查。

## 验证凭证

- 结构自检（呈批前机械跑）：
  `grep -c '^## ' Blueprint.draft.md` ≥ 6，且四段标题齐备
- 「元问答」≥3 条且均为领域问题（非"你同意吗"类确认题）
- 每个技术决策有领域后果翻译（好处/代价）
- 预演至少暴露一个潜在冲突
- 拒绝/修改结果经正常沉淀路径回注本技能「溯源」，不新造账本类型
